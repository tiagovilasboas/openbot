# REA openbot.run: Agentes e conversa

Fonte: clone do app desktop open-source openbot.run, commit a9b40aa (leitura apenas; nada executado). Caminhos abaixo são relativos à raiz do clone. Itens não lidos diretamente estão marcados "(inferido)".

## 1. Visão geral

- Um **agente** é um objeto persistente (id `agent-<uuid>`, workspace em `~/OpenBot/Agents/<id>`, projeção `projection_agents`) com perfil, provider/modelo, memórias, skills, rotinas e um chat principal ("main thread").
- Cada agente tem **threads laterais** (no código e no wire ainda chamadas de _task_): conversas paralelas com sessão de provider, fila e resultado próprios. Cada agente é uma "lane" no `DrainScheduler`; cada thread lateral é uma lane extra.
- O agente conversa por **fila de mensagens** (mailbox): mensagem enviada com o agente ocupado vira _steer_ (entra no turno corrente) ou _queue_, conforme o `busyMessageMode`.
- A UI é Solid (stores com draft), com um evento único `agent.onEvent` que um componente `agent-event-bridge` distribui para os domínios; o mesmo contrato serve desktop, web e mobile via Team API com capabilities opcionais.
- Extras: dock flutuante de agentes, painel lateral com panes, templates publicáveis por link, agentes ACP customizados, agentes que criam/configuram outros agentes por tools `openbot.*`.

## 3. Fluxos de interface

**Estrutura da tela de conversa** (`features/conversation`): `ConversationView` -> `ConversationHeader` (abas das threads + "+" + menu com grupo "Archived"), `ConversationTimeline` (maior arquivo, 1.836 linhas; virtualizado, agrupamento por dia, scroll rail, busca, pins, mensagens não lidas), `ConversationComposer`, `ConversationPanels` (painel lateral) e cartões inline.

**Estados do chat:** vazio (`AgentChatEmptyState`), trabalhando (linha de atividade com avatar com "humor": trabalhando, falha, espera), fila visível acima do composer, "Needs you" na barra lateral para pergunta/aprovação/takeover, banner de erro, aviso de limite de uso com escolha de destino da mensagem, "awaiting replies" quando o agente aguarda colegas.

**Cartões no fluxo:** pergunta (`ConversationQuestionPrompt`), bloco de UI, aprovação, takeover de browser, segredo de browser, sign-in MCP, sugestão de skill, sugestão de marketplace, instalação de servidor, rotina criada/alterada (agenda ou webhook), plano (checklist), subagentes, mudanças de memória, mudança de instruções, imagem/vídeo gerado, visual HTML (`ChatVisual`), tabela/diagrama/matemática.

**Composer:** editor rico com tokens (menção a agente `@[nome](id)`, skill, aba de browser, thread, MCP, anexo `attachment reference`), colar texto longo, arrastar arquivos, voz (gravação com waveform, transcrição local ou streaming em nuvem), rascunho persistido por conversa (`composer-draft-storage`), edição de mensagem da fila (persistida em `localStorage`), atalho de envio Enter ou mod+Enter (resolvido pelo dispositivo).

**Painel lateral** (`docs/architecture/side-panel.md`): registro `SIDE_PANEL_PANES`; abas de panes (Browser, Files, Settings, side question, subagente etc.), abas de arquivo e de threads. Fechar aba mostra, em ordem: vizinha, primeira thread, último arquivo, lista de panes. Cada agente/canal guarda suas abas; trocar de agente mantém aberto/fechado; fecha Settings/Files/preview ao trocar de agente. Panes de origem única (side question, subagente) não aparecem no launcher. Hooks `open`/`release` (ex.: pergunta lateral apaga ao fechar).

**Threads:** abas por agente guardadas por dispositivo em `localStorage` (`openbot:thread-tabs:v1`, até 50 abas; exclusões pendentes até 200). Aba de thread pode ir ao painel lateral e voltar. Salto "Branched from". Carregamento paginado: 100 mensagens iniciais, 50 por "Load older", 100 ao redor de um salto; só 5 conversas ocultas ficam em memória.

**Dock:** assentos (agente/canal) com avatar, selo de estado, chat compacto, prateleira de resultados; voz com store compartilhado do composer.

**Tasks rail:** lista agrupada por estado (`running`, `queued`, `idle`, `closed`), painel `TaskPanel`, exclusão com desfazer 6 s.

**Transições notáveis:** envio -> pending -> mensagem real; `turn-started` -> `turn-progress` -> `turn-completed` (ou `thread-turn-completed` p/ side threads, só local); `prompt`/`approval`/`browser-takeover-requested` -> "Needs you" -> `agent-input-resolved`.

**Skills e plugins** (`docs/architecture/skills-and-plugins.md`): skill = pasta com `SKILL.md` (frontmatter `name` + `description` 1-1024). OpenBot grava em `.agents/skills/` e `.claude/skills/` do workspace (cópia, sem link), registra hashes em `.openbot/skills-lock.json`, guarda desativadas em `.openbot/skills-disabled/`. Lê 7 pastas de workspace como somente leitura; `~/.agents/skills` (máx. 200) entra por `native`, `plugin` (Claude) ou `instructions` (máx. 100 itens, 300 chars de descrição). Biblioteca local com revisões imutáveis em `local-skills/<uuid>/<revisão>/bundle.zip`; limite 32 skills por agente. Plugin = MCP server + skills + texto de listagem, catálogo estático do Account Worker com cópia local.

**Capacidade e fila:** `TurnSlots` limita turnos simultâneos do servidor (2/8/16 por memória, ou valor do admin 1-128 / "unlimited"); quando cheio, prioridade a mensagem de pessoa, depois rotinas e colegas, mais antigo primeiro. Carência de início de turno 5 min (`TURN_START_GRACE_MS`).

## 5. Segurança e privacidade

- **Acesso do agente:** `full` (padrão) ou `workspace`. Em workspace cada provider é confinado: Codex em `workspace-write`, Claude com Bash em sandbox e pergunta antes de editar arquivo, demais por processo confinado (`workspaceEnforcement`: tool-sandbox, command-sandbox, confined-process). Pastas de skills do workspace são protegidas como configuração de projeto contra agentes confinados. Pastas adicionais e excluídas por agente.
- **Escalada bloqueada:** o roteador de tools só grava restrições; só o usuário amplia acesso/Computer Use, muda "Ask first / Full access" e liga scripts locais. A flag `allowAutomation` não é aceita pelo parser genérico da Team API nem por duplicação. Agente criado herda limites do criador (sandbox não se contorna via colega).
- **Aprovações:** por requisição, com `requestId` e handle opaco local; resposta casa handle+agente, handle expirado não responde a pedido posterior. Auto-aprovação por agente cobre comando/arquivo/permissões/MCP e publicação de site, mas nunca takeover de browser, e só o usuário a concede. Em threads laterais de rotina, ações com pessoas ausentes seguem as mesmas políticas (inferido).
- **Exclusão destrutiva:** `delete_agent` só por mensagem de pessoa, cartão do dono, mesmo com Full access; recusa rotina, canal, agente ou chat externo como origem.
- **O que nunca chega à UI:** valores de env de agentes ACP (só nomes), comandos/URLs/headers de MCP em `read_agent`, e-mail/credenciais/pastas de contas de provider em `list_models`, token da API local (arquivo 0600; instruções só citam caminhos), segredos de browser (cartão próprio, valores não aparecem no chat), conteúdo de segredos em template (publicação para se algo parece segredo), `trace` e `usage` de turno (ficam no computador; Team API remove).
- **Redação:** erros de provider são redigidos antes de ir à task/UI; a API local redige valores na saída; `history_*` só devolve trechos redigidos e só do próprio agente ou threads do mesmo agente (chat de mensageria só pesquisa a si mesmo; canal não tem histórico).
- **Entradas hostis:** rótulos/campos de `ask_ui` são texto puro, sem HTML; guards de runtime (`isConversationMessage`, `isAgentApproval` etc.) com limites em todo contrato; listener local recusa `Origin` e `Host` estranhos antes do token; rate limit por hora.
- **Privacidade de mensagens apagadas:** `deleteConversationMessage` remove o texto do log de eventos e replays (`scrubDeletedMessageEvents`); só mensagem própria de usuário sem turno ativo, salvo `deleteAny`.
- **Templates:** link público sem revisão; conteúdo é apenas o perfil + rotinas + skills; sem arquivos nem memórias; instalar exige clique.
- **Notificações:** turnos entre agentes não notificam; rotinas silenciosas não notificam nem contam como não lidas.

## 6. Observações para o nosso produto (síntese, inferido)

- O desenho em "port" + capabilities opcionais é o que permite o mesmo núcleo servir desktop, web e mobile; vale replicar a ideia de contratos congelados com extensões opcionais.
- Padrões reutilizáveis: envio idempotente por `clientMessageId` com linha otimista; steer/queue como modo por agente; lanes por thread com `hold` explícito; exclusão com desfazer e commit tardio; stores de eventos únicos que só apontam para baixo.
- Riscos observados: `conversation-scope.ts` com 2.912 linhas e `ConversationTimeline.tsx` com 1.836 mostram o custo de centralizar; nosso limite de 300 linhas por arquivo exige separar por domínio desde o início.
